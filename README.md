## 1. 한눈에 보는 서비스

**서비스 이름:** 날짜별 인기뉴스 AI 큐레이션 (Daily Hot News AI)  
**해결하려는 문제:** 특정 날짜에 관한 뉴스를 찾아 기사별 제목을 비교하고 주요 흐름을 파악하는 번거로움  
**대상 사용자:** 과거 또는 현재의 시사·기술 이슈를 날짜와 키워드로 빠르게 찾아보고 싶은 학습자·일반 사용자

원본 `AI-A1-3`에서는 FastAPI, GDELT 뉴스 API, OpenAI API, HTML·CSS·JavaScript를 활용해 뉴스 검색 및 요약 기능을 구현하려고 했습니다. 원본 README에는 개발 중 발생한 검색 버튼 연결 문제, 개발 경로 문제, GDELT 요청 제한 등을 파악하고 해결 방법을 정리한 기록이 있습니다. 이러한 **문제 확인과 학습 과정**도 평가할 만한 장점입니다. 다만 원본 README에 설명된 완료 상태가 실제 소스·배포 결과까지 모두 입증하는 것은 아닙니다.

**이후 보완한 개발본**에서는 프론트엔드와 Vercel용 Python API를 분리하고, 입력 검증·오류 안내·기사 링크 안전 처리·다크 모드·자동 테스트를 추가했습니다. 프로젝트 설명에서 원본 작업과 추가 보완을 혼동하지 않도록 하세요.

## 3. 왜 다크 모드를 평가할 수 있는가 — 보너스 과제의 핵심

과제 명세 4쪽의 선택 보너스에는 **다크 모드/마이크로 인터랙션/방문자 분석 중 하나 이상을 적용하여 사용자 경험(UX)을 고도화**하는 항목이 있습니다. 현재 개발본은 다크 모드에 집중했습니다. 이전 평가에서 다크 모드를 수행한 것으로 인정했던 기준과 일관되게, 최종 작업본에서도 이를 구체적으로 보여주는 것이 중요합니다.

| 확인할 기능 | 구현 방식 | 직접 확인하는 방법 |
|---|---|---|
| 수동 테마 전환 | `index.html` 헤더의 `#themeToggle` + `js/theme.js` | 버튼을 누르면 라이트↔다크 전환 |
| 전체 화면에 일관된 색상 | CSS 사용자 정의 속성 `--page`, `--surface`, `--text`, `--border` 등 | 헤더·검색창·AI 요약·뉴스 카드·이용 방법·소개·푸터를 위에서 아래까지 비교 |
| 최초 방문 시 OS 설정 반영 | `matchMedia('(prefers-color-scheme: dark)')` | **저장된 테마 설정이 없을 때만** 운영체제 테마 변경 확인 |
| 선택 유지 | `localStorage` 키 `daily-hot-news-ai-theme` | 원하는 테마 선택 후 새로고침·재방문 |
| 다른 탭과 동기화 | `storage` 이벤트 감지 | 동일 사이트를 두 탭에서 열어 설정 전환 |
| 접근성 | `aria-label`, `title`, `:focus-visible`, `prefers-reduced-motion` | 키보드 Tab, 버튼 이름, 움직임 줄이기 설정 확인 |
| 모바일 대응 | `@media (max-width: 800px)` 및 `430px` | 화면 너비를 375px 등으로 변경하고 버튼/메뉴 배치 확인 |
| 테스트 | `tests/test_theme.cjs` 6개 | `node --test tests/test_theme.cjs` |

**평가 시 강조할 점:** 버튼 하나만 어둡게 만든 것이 아니라, 디자인 토큰을 공통으로 적용해 여러 UI 요소의 일관성을 유지하고 사용자의 선택을 저장하도록 구현했다는 점입니다. 단, 색 대비의 정량 접근성 검사(WCAG 적합 판정)까지 완료했다고 주장하지 마세요.

## 4. 실제 데이터 처리 흐름

```text
[사용자: 날짜 + 키워드 입력]
             |
             v
[index.html의 폼 / js/app.js]
  - 빈 입력 확인
  - fetch('/api/news?date=...&keyword=...')
             |
             v
[api/news.py / GET /api/news]
  - 날짜·검색어 검사
  - GDELT 뉴스 검색 API 요청
  - 최대 10건의 기사 정보 정리
  - OPENAI_API_KEY가 있으면 OpenAI API에 제목 목록 전달
  - 성공·미설정·실패·검색 결과 없음 상태 구분
             |
             v
[JSON 응답]
  - count / articles / summary / summary_mode / summary_error / from_cache
             |
             v
[js/app.js]
  - 요약 영역에 텍스트 표시
  - 제목·기사 링크를 카드로 표시
  - 오류 또는 안내 메시지 표시
```

**핵심 한계:** 이 프로젝트는 **기사 원문 전체를 읽고 요약하는 방식이 아니라, GDELT에서 받은 기사 제목을 근거로 공통 흐름을 요약**하도록 작성되어 있습니다. 제목만으로 기사 내용 전체를 검증할 수 없으므로 화면에 원문 확인 안내가 있으며, 평가 설명에서도 이를 정확히 밝혀야 합니다.

외부 데이터는 GDELT를 사용합니다. 조회 결과가 0건일 수도 있고 요청 제한·데이터 가용 기간·언어 구성에 따라 기대와 다른 결과가 나올 수 있습니다. 이를 무조건 프로그램 오류라고 판단하지 말고 서버 응답을 먼저 살펴보세요.

## 6. 테스트 근거와 테스트가 입증하지 못하는 것

`tests/test_news.py`의 6개 단위 테스트: 잘못된 날짜, 빈 키워드, 미래 날짜, 모의 GDELT 응답 처리, OpenAI 키 미설정 상태/캐시, GDELT 429 응답. 외부 서비스를 **가짜 응답(mock)** 으로 대체합니다.

`tests/test_theme.cjs`의 6개 단위 테스트: OS 라이트/다크 감지, 저장 설정 우선순위, 버튼 전환과 접근성 레이블, OS 설정 실시간 변경, 탭 간 동기화, 저장소 사용 제한 시 동작.

2026-11-17 기준 이 문서를 준비하면서 두 명령을 실행했고 **12개가 통과**했습니다.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
node --test tests/test_theme.cjs
```

자동 테스트 통과는 실제 GDELT 호출, 유료 OpenAI API 호출 성공, Vercel 배포 상태, 모든 기기에서의 접근성을 보장하지 않습니다. 이 구분을 지켜야 평가 내용의 신뢰도가 높아집니다.

## 7. 평가에서 설명할 만한 강점

1. **명확한 사용자 문제:** 날짜와 키워드라는 간단한 입력으로 여러 기사와 주요 흐름을 함께 확인하도록 설계했습니다.
2. **실제로 배울 만한 기술 연결:** 폼 입력 → JavaScript 비동기 통신 → Python API → 외부 뉴스/AI API → JSON 결과 → DOM 출력이라는 전체 흐름을 포함합니다.
3. **원본의 오류 분석 과정:** 양선재 님의 원본 README에는 버튼 ID·경로·GDELT 제한 등 개발 과정에서 만난 문제를 분석한 기록이 있습니다.
4. **유지보수를 고려한 구조:** 현재 작업본은 `index.html`, `css/`, `js/`, `api/`, `tests/`, `docs/`를 역할별로 구분합니다.
5. **사용자 경험 개선:** 다크 모드, 선택 유지, OS 설정 인식, 모바일 스타일, 입력·실패 안내를 적용했습니다.
6. **보안·한계에 대한 인식:** 키를 환경 변수로 관리하고, 기사 제목 기반 요약이라는 한계를 명시했습니다.
7. **검증 가능한 자료:** 단위 테스트 코드, 과제 요건 점검표, 기획서 초안, 원본 대비 수정 기록이 있습니다.

## 8. 동료 평가 의견 예시 — 긍정적이되 검증 범위 구분

아래 문장은 **배포 전 자료를 평가하는 경우**에 활용할 수 있는 예시입니다. 평가자가 실제로 보지 못한 기능의 성공을 단정하는 문장은 넣지 않았습니다.

> 날짜와 키워드를 이용해 원하는 시점의 뉴스를 검색하고 AI로 주요 흐름을 요약하려는 아이디어가 분명하여, 실제 사용자가 어떤 상황에서 서비스를 활용할지 쉽게 이해할 수 있었습니다. 단순한 정적 소개 페이지를 넘어서 사용자 입력과 외부 뉴스 API, Python 백엔드, AI 요약 기능을 하나의 서비스 흐름으로 연결하려고 한 점이 좋았습니다. 특히 원본 개발 기록에는 검색 버튼이 동작하지 않았던 문제, 파일 경로 문제, 외부 뉴스 API의 요청 제한 등을 살펴보고 해결 방향을 정리한 과정이 남아 있어, 코드를 만드는 것뿐 아니라 오류의 원인을 찾는 학습 과정이 드러납니다.
>
> 이후 보완된 개발본에서는 HTML·CSS·JavaScript와 API의 역할을 분리하고, 날짜와 검색어의 유효성을 확인하며, 기사 목록과 AI 요약 상태를 구분해 표시하도록 구성한 점이 인상적이었습니다. 사용자가 잘못된 값을 입력하거나 외부 서비스에서 문제가 발생했을 때 안내 문구를 제공하려는 부분도 사용자 관점에서 의미가 있습니다. 기사 전체가 아니라 제목을 근거로 요약한다는 서비스의 한계를 밝히고 원문 링크를 제공하는 점 역시 신뢰성을 고려한 설계라고 생각합니다.
>
> 선택 보너스 과제인 사용자 경험 개선 측면에서는 다크 모드를 일관되게 적용한 점을 높이 평가하고 싶습니다. 화면의 일부 색만 바꾸는 데 그치지 않고 헤더, 검색 영역, 뉴스 카드, 요약 패널, 안내와 푸터까지 공통 색상 체계를 적용했으며, 운영체제 테마 인식과 사용자 설정 저장도 구현했습니다. 모바일 화면과 키보드 사용을 고려한 점까지 포함해 단순 기능 추가보다 서비스 완성도를 높이려는 방향이 드러납니다. Python 및 JavaScript 자동 테스트가 마련되어 있어 구현 내용을 검토하기에도 좋았습니다.
>
> 향후 실제 API 연동 결과와 Vercel 배포 URL, 데스크톱·모바일 동작 증빙을 추가하면 과제의 구현 성과가 더욱 명확해질 것입니다. 현재 자료에서는 이를 완료했다고 판단하지 않지만, **아이디어의 구체성, 문제 해결 과정, 프론트엔드와 백엔드 연동 설계, 사용자 경험 개선 노력**은 긍정적으로 평가할 충분한 근거가 있다고 생각합니다.

**배포 완료 후에만 추가할 문장:** "실제 배포 URL에서 날짜·키워드 검색, 기사 목록, AI 요약, 반응형 레이아웃, 라이트·다크 모드 전환을 직접 확인하였으며 ..." — 반드시 직접 검증하고 해당 기능이 정상일 때만 사용하세요.

## 9. 평가자가 물을 수 있는 질문과 답변 요지

**Q. 일반 뉴스 검색 사이트와 차이점은 무엇인가요?**  
A. 특정 날짜를 직접 지정해 주제별 기사 제목을 모으고, AI가 제목들의 공통 흐름을 간단히 정리하도록 기획했습니다. 실시간 인기 순위 산정 서비스를 구현한 것은 아닙니다.

**Q. AI는 무엇을 입력받고 무엇을 반환하나요?**  
A. 날짜·검색어 검색 결과의 기사 제목 최대 10개와 키워드를 받아, 한국어 3문장 이내의 제목 기반 흐름 요약을 요청합니다. 기사 본문을 읽는 기능은 구현되지 않았습니다.

**Q. API 키를 넣지 않으면 어떻게 되나요?**  
A. 뉴스 검색이 성공했다면 기사 목록은 확인할 수 있고 AI 요약은 설정 필요 상태(`unconfigured`)로 표시합니다. 키가 없는데 AI 요약이 성공한 것처럼 보여주지 않습니다.

**Q. 다크 모드가 단순 색상 변경 이상의 보너스 기능인 이유는?**  
A. CSS 변수 기반으로 전체 UI에 공통 적용하고, OS 선호 설정 반영, 사용자가 선택한 테마 저장, 새로고침 후 복원, 탭 간 동기화, 모바일 화면을 고려했기 때문입니다.

**Q. 캐시는 어떤 역할을 하나요?**  
A. 같은 조건의 반복 요청 때 180초 동안 서버 인스턴스의 임시 결과를 재사용하도록 작성했습니다. Vercel 인스턴스마다 캐시가 별도로 존재할 수 있으므로 전역·영구 저장소는 아닙니다.

**Q. 무엇이 아직 남았나요?**  
A. 실제 GDELT·OpenAI API 성공 확인, 본인 GitHub 저장소에 커밋·푸시, Vercel 배포 및 URL 검증, 진짜 스크린샷과 AI 코딩 도구 사용 기록 확보입니다.
